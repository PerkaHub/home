# 0005. Отказаться от кеша финансовых статусов и сериализовать оплату

- **Статус**: принято
- **Дата**: 2026-11-07
- **Участники проекта**: Белянский Глеб, Опекин Егор, Рогачев Егор
- **Основание принятия**: проектный выбор по поручению владельца проекта от 07.11.2026

## Контекст

Быстрый интерфейс и повтор запроса не должны создавать ложный успех и дубли.

## Движущие факторы

FR-04/05, NFR-01/02: конфликт скорости, доступности и согласованности; C-05: только sandbox. Источники: [требования](../requirements.md), [агрегаты](../domain/aggregates.md).

## Рассмотренные варианты

| Вариант | За | Против |
|---|---|---|
| Основная PostgreSQL без финансового кеша | Актуальное состояние и атомарность | Нагрузка и ожидание при неопределённости |
| Кеш статусов и разрешённый новый платёж при тайм-ауте | Меньше ожидания, быстрый ответ | Устаревший статус и риск повторного списания |

## Решение

Чтение статуса только из db. Блокировка Charge, уникальный активный charge_id, уникальные user_id+idempotency_key и provider_event_id. Суммы предложений фиксируются до создания попытки. Внешний вызов после commit с постоянным merchant id; неопределённость сохраняет pending, worker каждые 60 с подбирает created и pending по next_attempt_at и истечению аренды. Сохранённая попытка — поручение на отправку после commit; повтор использует тот же ключ провайдера и неизменный снимок запроса. Порядок восстановления задан в [протоколе](../architecture/payment-recovery.md). Успех требует аутентичности события и совпадения id, RUB и полной суммы. Несовпадение — журнал и ручной разбор, не успех. Подпись webhook и алгоритм сверки уточняются после выбора провайдера до ЛР 4; адаптер до этого не считается готовым.

Определяющий довод — NFR-02: финансовая корректность важнее мгновенного повторного запуска.

## Последствия

Положительные: Актуальное состояние и атомарность. Отрицательные: Ожидание при сбое провайдера; дополнительная координация и ограничения БД. Что пересмотрит решение: Доказанная нехватка производительности NFR-01 или провайдер без нужной идемпотентности.


### Порядок внешних ответов

Сохранённый attempt_id используется как merchant id. Если webhook пришёл до ответа create, аутентичное событие сопоставляется по merchant id с проверкой суммы и RUB (AC-05.6). Если контракт sandbox не передаёт merchant id и связать событие с попыткой пока нельзя, endpoint отвечает 503 для повторной доставки после получения provider_id; worker дополнительно сверяет попытку по API. До сопоставления payment_event не создаётся, неизвестная попытка не погашается. Поздний ответ create не понижает итоговое состояние. Повтор provider_event_id с другим payload_hash не применяется: несовпадение регистрируется для сверки (AC-05.5). Обычный идентичный дубль принимается без повторного финансового эффекта.
