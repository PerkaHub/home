## Общие правила и спорные ответы

Все закрытые операции дополнительно возвращают 401 без действующей сессии, 403 при неверной роли/CSRF; принадлежность проверяется сервером. Чужой и неизвестный объект — 404. Валидация — 422, бизнес-конфликт — 409. POST возвращает Location при 201. Запросы staff ограничены собственной организацией/домом. Черновики доступны только авторизованному сотруднику нужной роли.

Публикация выражена подресурсом publications, а не глаголом publish. Изменение опубликованного документа и DELETE финансовой истории не предусмотрены. Ошибки оформляются как Problem Details по RFC 9457, Content-Type: application/problem+json. Поля и пример приведены ниже.

Повтор POST payment-attempts с тем же пользователем, ключом и телом возвращает ту же попытку: 200, либо 202 при pending. То же значение ключа с другим телом — 409. При тайм-ауте внешнего create сервер сохраняет pending и возвращает 202; новая попытка после подтверждённого отказа требует нового ключа и действующего quote. Успешная попытка блокирует оплату начисления навсегда в рамках MVP.

Webhook без подписи — 401, битый JSON — 400, несовпадающая сумма/валюта — 422 и диагностическое событие без изменения статуса; временная недоступность db — 503. Точный формат и криптографическая проверка определяются контрактом выбранного sandbox до ЛР 4. После commit дубль получает 204. Внешняя интеграция пока не проверена.

Служебный /internal не опубликован через nginx наружу. Планировщик вынесен за границу продукта на обеих схемах C4; доступ идёт через внутренний HTTPS-шлюз стенда. Он запускает разовую сверку через API, worker независимо выполняет регулярную; оба используют блокировку строк, дубль не меняет итог.

История: limit 1–100, сортировка created_at DESC, id DESC; курсор содержит обе границы. Детали и все списки фильтруются по Membership. Возврат с платёжной формы ведёт только к чтению GET статуса.


### Порядок внешних ответов

Сохранённый attempt_id используется как merchant id. Если webhook пришёл до ответа create, аутентичное событие сопоставляется по merchant id с проверкой суммы и RUB (AC-05.6). Если контракт sandbox не передаёт merchant id и связать событие с попыткой пока нельзя, endpoint отвечает 503 для повторной доставки после получения provider_id; worker дополнительно сверяет попытку по API. До сопоставления payment_event не создаётся, неизвестная попытка не погашается. Поздний ответ create не понижает итоговое состояние. Повтор provider_event_id с другим payload_hash не применяется: несовпадение регистрируется для сверки (AC-05.5). Обычный идентичный дубль принимается без повторного финансового эффекта.


## Ошибки: RFC 9457

Контракт API использует [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html). В проекте заданы поля type (URI типа проблемы), title (краткое название типа), status (число, совпадающее с HTTP-кодом), detail (пояснение конкретной ошибки), instance (URI конкретного обращения). Расширения: code — стабильный код приложения; correlation_id — идентификатор для журнала; errors — список ошибок валидации с pointer и detail. Это состав проектного контракта; RFC допускает необязательность стандартных полей.

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
```

```json
{
  "type": "urn:domprozrachno:problem:active-payment",
  "title": "Платёж уже обрабатывается",
  "status": 409,
  "detail": "Дождитесь результата текущей попытки.",
  "instance": "/v1/problems/8a6cd174-17ce-4bec-8874-0d42d70b0e82",
  "code": "ACTIVE_PAYMENT_EXISTS",
  "correlation_id": "8a6cd174-17ce-4bec-8874-0d42d70b0e82"
}
```

urn задаёт идентификатор типа, не адрес страницы. instance служит идентификатором обращения и не обещает публичный endpoint чтения журналов. В 404 для чужого и неизвестного ресурса совпадают тип, title и detail; стек, секреты и сведения о чужом счёте не включаются. Клиент разбирает type/code, а не текст detail.

## Восстановление отправки

POST payment-attempts сохраняет поручение до сетевого вызова. Worker обрабатывает created и pending; сбой между commit и create покрыт AC-05.7. Поздний create-ответ и тайм-аут обновляют статус только из created и не изменяют succeeded/rejected. После replay_until новый create запрещён, выполняется только сверка по AC-05.8. Детали: [протокол восстановления](../architecture/payment-recovery.md).

GET payment-attempts/{id} дополнительно возвращает reconciliation_required: true, если требуется сверка после исчерпания срока безопасного create или противоречивого результата. Это признак текущей попытки, не отдельная система задач.
