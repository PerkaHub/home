# Обзор архитектуры

«ДомПрозрачно» соединяет доступ к счёту, публикацию начислений и расходов, тестовую оплату. Граница: один дом, синтетические данные, внешний sandbox; реальных переводов и расчёта тарифов нет. Контексты из [модели событий](../domain/event-storming.md) — модули одного приложения. Каталог [диаграмм](README.md) задаёт читателя и вопрос, исходники — Mermaid.

## Защищённость: пять принципов

1. Минимальные привилегии: бухгалтер не выдаёт приглашения; житель читает свой счёт.
2. Запрет по умолчанию: нет Membership — нет доступа; новые операции закрыты до явного разрешения.
3. Проверка каждого обращения: права проверяет application на сервере для каждого id, в том числе во вложенных ресурсах.
4. Несколько уровней защиты: HTTPS, cookie, CSRF, авторизация, ограничения БД.
5. Минимизация данных и поверхности: синтетические сведения, секреты вне Git, внутренний endpoint скрыт nginx.

| STRIDE | Проявление | Предусмотренная защита | Реализация |
|---|---|---|---|
| Spoofing | Подделка жителя или webhook | Сессия, Argon2id, проверка провайдера | ЛР 4Б |
| Tampering | Подмена суммы клиентом | Снимок quote, пересчёт сервера и сверка суммы | ЛР 4 |
| Repudiation | Отрицание публикации/смены статуса | Автор, дата, correlation_id, hash события | ЛР 3/4 |
| Information disclosure | Чужой счёт или секрет в логах | Membership, одинаковый 404, маскирование | ЛР 4Б |
| Denial of service | Перебор входа, поток webhook | 5 неудачных входов/мин. на логин+IP, 429; предел тела 64 КБ | ЛР 4Б |
| Elevation of privilege | Житель публикует начисления | Роли и дом организации проверяет сервер | ЛР 4Б |

Меры защиты реализуются в ЛР 3 и ЛР 4. За пределами MVP: MFA, внешний SSO, промышленный WAF, независимый аудит и реальные персональные данные. Причина — C-01/C-03; переход к реальному пилоту требует отдельного пересмотра модели угроз и ADR-0004.

## Что осознанно не сделано

Redis и брокер отсутствуют: очереди сообщений не требуются для выбранного протокола; worker сверяет состояния из PostgreSQL, доменные события пока обрабатываются внутри приложения после commit. При необходимости надёжных внешних подписчиков потребуется ADR об outbox и доставке. Нет микросервисов, C4-компонентов, OpenAPI и миграций — соответствующие этапы курса ещё впереди.


## Принятые правила пилота

- Архитектура: модульный монолит access/billing/transparency, отдельный worker, одна PostgreSQL. Финансовые статусы читаются из основной БД без кеша; брокер не используется.
- Доступ: серверные сессии, Argon2id, проверка роли и принадлежности дому на сервере. Представителя организации назначает администратор при подготовке стенда; житель не может назначить себе роль или привязку.
- Расходы: в MVP публикуются категории и суммы; подтверждающие документы относятся к v1.1. Понятность категорий проверяется на учебных заданиях.
- Платёж: сохраняемое поручение в PaymentAttempt, worker обрабатывает created/pending с арендой, повторяет неизменный запрос с прежним ключом в пределах replay_until. После этого разрешена только сверка. Итоговое состояние не понижается.
- Внешний sandbox выбирается при подготовке интеграции по обязательному контракту из payment-recovery.md. Проверка доступа и контракта относится к ЛР 4; архитектура не зависит от названия поставщика.

Основание фиксации решений: поручение владельца проекта от 07.11.2026. Пять ADR имеют статус «принято»; условия пересмотра сохранены в каждой записи.
