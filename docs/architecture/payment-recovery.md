# Восстановление платёжной попытки

Проектный протокол FR-05, NFR-02 и ADR-0005. Он задаёт поведение будущей реализации и проверяемые сценарии ЛР 4–5.

## Состояния и надёжное поручение

`created` — согласие принято, попытка и снимок запроса сохранены; отправка может ещё не состояться. `pending` — провайдер принял запрос либо результат внешнего вызова неопределён. `succeeded` и `rejected` — проверенные итоговые состояния. Сетевой тайм-аут не переводит попытку в `rejected`.

Строка PaymentAttempt служит сохраняемым поручением на отправку. В одной транзакции с блокировкой Charge сохраняются attempt_id, снимок условий, `provider_request` без платёжных реквизитов, постоянный ключ провайдера `attempt_id`, `next_attempt_at`, `lease_until`, `lease_token`, `dispatch_attempts = 0`. Отдельная очередь не требуется: worker читает поручения из PostgreSQL.

Согласие и срок quote проверяются перед созданием попытки. Восстановление уже принятой попытки использует её неизменный снимок, даже если срок первоначального предложения затем истёк. Новый платёж после подтверждённого отказа требует нового согласия.

## Отправка и восстановление

1. API резервирует отправку на 30 секунд с уникальным lease_token при создании поручения, затем выполняет commit. Внешний HTTP-вызов — после commit, тайм-аут 10 секунд.
2. Worker каждые 60 секунд выбирает **created и pending**, у которых `next_attempt_at <= now` и аренда отправки отсутствует либо истекла. Короткая транзакция с `FOR UPDATE SKIP LOCKED` назначает новый lease_token и lease_until, увеличивает dispatch_attempts. Сетевой вызов не удерживает транзакцию и блокировку.
3. Для created worker сначала запрашивает состояние по merchant id. При найденной операции применяет результат. Если операция не найдена, повторяет create с **тем же ключом и тем же provider_request**. Даже если первый запрос успел дойти до провайдера, его идемпотентный контракт возвращает ту же операцию.
4. Для pending worker сверяет состояние. Если после неопределённого create провайдер ещё не находит операцию, разрешён тот же идемпотентный create в пределах гарантированного срока хранения ключа. Сам по себе ответ «не найдено» не подтверждает отказ.
5. Результат записывается в новой транзакции с порядком блокировок Charge → PaymentAttempt. Обычный ответ create может изменить только created → pending. Если состояние уже pending или итоговое, статус сохраняется; совместимые provider_id и URL можно дополнить. Противоречивый provider_id направляется на сверку, а не перезаписывается.
6. Изменения служебной аренды принимаются только при совпадении lease_token. Старый обработчик не снимает чужую аренду. Webhook и проверенный итог сверки используют общий обработчик терминального результата независимо от аренды.
7. При тайм-ауте или недоступности провайдера created становится pending условным обновлением только из created; pending остаётся pending. Итоговый статус сохраняется. Повторные сверки назначаются через 60, 120, 240 секунд, затем каждые 300 секунд. После восстановления API/worker незавершённые поручения автоматически продолжаются из БД.

При исправных worker и БД поручение после сбоя между commit и сетью будет подобрано не позднее 90 секунд: 30 секунд аренды плюс один цикл опроса. Достижение внешнего успеха зависит от доступности провайдера.

## Требования к тестовому провайдеру

Перед интеграцией проверяются идемпотентный create с постоянным ключом, повторное получение той же операции, поиск по merchant id и срок хранения ключа не менее 24 часов. `replay_until` сохраняет подтверждённую контрактом границу безопасного повтора. После неё **create не повторяется**: продолжаются только запросы статуса и устанавливается reconciliation_required и формируется диагностическое событие для оператора. Неопределённая попытка остаётся видимой как ожидающая; новая оплата блокируется до достоверного результата. Автоматически объявлять отказ ради снятия блокировки нельзя.

Таким образом, короткий сбой не оставляет created без обработчика. Длительная недоступность внешней системы обозначается состоянием и диагностикой, а не скрытой бессрочной задачей отправки.

## Порядок событий и защита от повторов

Проверенный webhook может первым перевести created → succeeded/rejected. Поздний ответ create и тайм-аут не понижают итоговое состояние. Первый проверенный итог применяется один раз; противоположный итог вызывает сверку, без автоматической смены статуса. Повтор event_id с тем же payload_hash принимается без эффекта, с другим hash — регистрируется как конфликт. merchant id, RUB и сумма проверяются до изменения Charge.

## Сценарии проверки

| Сбой или порядок | Ожидаемое восстановление | Критерий |
|---|---|---|
| Commit состоялся, API завершился до вызова create | Worker подбирает created после истечения аренды и отправляет сохранённый запрос | AC-05.7 |
| Провайдер создал платёж, API завершился до записи ответа | Worker находит операцию либо безопасно повторяет тот же ключ; внешняя операция одна | AC-05.7 |
| Worker завершился после получения аренды | Другой цикл подбирает поручение после lease_until; устаревший обработчик не сбрасывает новую аренду | AC-05.7 |
| Webhook success раньше create-ответа или тайм-аута | Состояние остаётся succeeded, погашение одно | AC-05.6 |
| Provider недоступен дольше replay_until | Только сверка статуса и диагностический признак, без нового create и ложного отказа | AC-05.8 |

Иллюстративная модель переходов: `python scripts/check_payment_protocol.py`. Она проверяет порядок событий в проектном протоколе; интеграционные испытания провайдера относятся к ЛР 4–5.
