# «ДомПрозрачно»: процесс команды

Процесс команды из трёх участников. Состав, распределение ответственности, гибкий график и выбор инструментов подтверждены командой. Календарные даты и фиксированное время встреч не задаются; план ведётся по учебным неделям.

|---|---|---|

Все пишут документы и код последующих модулей. Ответственный за качество не принимает единолично собственную работу: проверяет другой участник. Для задач Глеба проверяющим по умолчанию выступает Рогачев Егор, для задач Рогачева Егора — Опекин Егор, для задач Опекина Егора — Глеб. При недоступности назначенного проверяющего ревью выполняет третий участник.

## Облегчённый Scrum

Цикл — одна неделя. Один упорядоченный бэклог соответствует карте историй; цель первого продуктового выпуска — основной путь MVP. Отдельные должности Scrum Master и Product Owner не создаются; обязанности фасилитации и приоритизации совмещаются с указанными зонами.

Каждая задача содержит ID истории, цель, критерии приёмки, исполнителя, проверяющего, зависимости и размер S/M/L. Оценки делаются одновременно; расхождения обсуждаются. Задача L разбивается на проверяемые части. Изменения финансового сценария не режутся на «всю базу», «всё API» и «весь интерфейс».

Доска: **Бэклог → Готово к работе → В работе → На проверке → Готово**. На человека не более одной задачи «В работе»; для команды не более двух задач «На проверке». Блокировка отмечается в задаче, не скрывается новым начатым объёмом. Приоритет Must выше Should/Could, и в обязательный план не добавляются истории v1.1/v1.2.

## Definition of Ready — можно брать в цикл

- [ ] Есть ID US, релиз, полная формулировка и ожидаемый наблюдаемый результат.
- [ ] Записаны минимум основной и ошибочный/граничный сценарии «Дано — Когда — Тогда». Для всех Must они уже есть в [user-story-map.md](user-story-map.md); поздние истории уточняются до начала работы.
- [ ] Определены роль и область доступа: свой дом/организация/лицевой счёт; подготовлены синтетические данные.
- [ ] Для денежных изменений названы суммы, комиссия, округление, допустимые состояния и источник подтверждения.
- [ ] Указаны зависимости; нужный внешний тестовый доступ доступен либо отдельная исследовательская задача явно помечена как таковая.
- [ ] Понятно, какое изменение увидит пользователь и как проверяющий воспроизведёт результат.
- [ ] Назначены исполнитель и другой проверяющий; команда оценила задачу, объём помещается в недельный цикл.
- [ ] Нет открытого вопроса, способного изменить критерий успеха; допущения записаны.

## Definition of Done — можно принять без автора

### Для документов текущей лабораторной

- [ ] Файлы заполнены; ID, релизы, Must, персоны, границы и вехи совпадают между документами.
- [ ] Выполнены проверки ссылок, Mermaid, XML, геометрии карточек и соответствия PNG исходной карте; результат проверок сохранён или приложен к задаче.
- [ ] Второй участник прочитал изменения, открыл редактируемую карту и оставил содержательный результат ревью; автор устранил замечания.
- [ ] Обновлён docs/CHANGELOG.md; для открытых вопросов указаны ответственные и сроки проверки.
- [ ] После передачи файлов на другое окружение проверяющий открывает документы, карту и экспорт по инструкции; фактический результат указан в задаче.

Тема одобрена преподавателем. Перед сдачей запланированы ревью другим участником и репетиция защиты.

### Для реализации в последующих модулях

- [ ] Изменение связано с US и удовлетворяет всем её критериям; для платежа проверены успех, отказ, ожидание, повтор запроса/события и неверное подтверждение.
- [ ] Написаны и проходят проверки принятого поведения, включая чужой счёт/дом и неправильные суммы; после М02 они выполняются в настроенном конвейере. Проверки не отключены ради зелёного результата.
- [ ] Запрос на слияние проверен другим участником; результат ревью виден, блокирующие замечания закрыты; изменение влито в основную ветку.
- [ ] Обновлены затронутые инструкции, контракт, состояния и документы docs/; рядом с US есть способ воспроизведения результата.
- [ ] В docs/CHANGELOG.md добавлена запись о фактическом изменении; после переноса журнала в М02 используется согласованное расположение в корне.
- [ ] Проверяющий поднял чистое тестовое окружение по инструкции и повторил сценарии; сохранены команда проверки и результат. «Работает у автора» недостаточно.
- [ ] Для US-09 есть свидетельство внешней тестовой операции; для US-10 — проверенного результата провайдера. Эмулятор помечен отдельно и не засчитывается за внешний контур.
- [ ] В выводе нет реальных данных жильцов, реквизитов и секретов интеграции; тестовая оплата ясно обозначена пользователю.

Это правила будущей реализации: в лабораторной №1 приложение, база, репозиторий и CI/CD не создавались.

## Ритм и доступность

Команда работает по гибкому графику без фиксированных дней и времени встреч. В начале каждого недельного цикла участники согласуют доступность в Telegram. При назначении созвона указывают время в часовом поясе Asia/Omsk.

| Событие | Когда | Длительность | Наблюдаемый результат |
|---|---|---|---|
| Планирование цикла | Один раз в начале недельного цикла, время согласуется в Telegram | До 25 минут | Цель недели, выбранные готовые задачи, исполнитель/проверяющий, доступный объём |
| Короткая синхронизация | По необходимости при блокировке или изменении плана; в чате либо созвоном | До 10 минут | Обновлены блокировки и прогноз; при необходимости привлечена помощь |
| Показ результата и разбор процесса | Один раз в конце недельного цикла, время согласуется в Telegram | До 25 минут | Пройден пользовательский сценарий, записаны замечания и одно улучшение процесса |
| Асинхронное обновление | В рабочие дни участников | До 3 минут | В задаче: результат, следующий шаг, препятствие |

Постоянная норма часов не устанавливается. Перед каждым циклом Глеб, Опекин Егор и Рогачев Егор сообщают доступный объём работы; на этой основе команда выбирает задачи. Учёба и другие занятия уменьшают объём цикла. Прогноз уточняется по фактически завершённым задачам, без заранее объявленной скорости.

## Использование AI-инструментов

При редактуре постановки проблемы ИИ предложил три варианта:

1. «Жителю приходится искать начисления, оплату и сведения о расходах дома в квитанциях, таблицах и переписке, поэтому он не может быстро проверить итог; сотрудники УК/ТСЖ и бухгалтер повторяют ответы и вручную сверяют данные».
2. «Жильцы одного дома не видят в одном месте состав начисления, опубликованные расходы и достоверный статус оплаты; управляющая организация тратит время на повторные разъяснения».
3. «Разрозненные сведения о начислениях, расходах и оплате мешают жителю проверять итог, а сотрудникам УК/ТСЖ — согласованно объяснять данные и сверять платежи».

Рабочей редакцией выбрана комбинированная формулировка из [requirements.md](requirements.md): в ней сохранены разрозненность сведений, затронутые пользователи и последствия для каждой стороны. Постановку проблемы нужно уточнить по результатам интервью.

## Решения и изменение требований

1. Продуктовое решение обсуждают все; ответственный за требования записывает проблему, варианты, выбранный вариант, причину и затронутые ID прямо в задаче/документе. Решения об объёме отражаются также в CHANGELOG.
2. Если за 15 минут нет согласия, формулируют вопрос и варианты для преподавателя. До решения продолжают независимую работу, не реализуя спорное необратимое изменение.
3. Изменение Must одновременно отражается в requirements, CJM при необходимости, карте .drawio, её PNG и Markdown, плане и журнале. Добавление истории требует назвать, что вытесняется из доступного времени.
4. Решения по архитектуре принимаются в соответствующих модулях; с М07 оформляются архитектурные решения. Стек в этой работе не утверждается.
5. При отставании сначала используют общий буфер и снимают необязательную работу. Задачи без внешнего доступа, успешного теста или ревью остаются открытыми.

После каждого цикла фиксируются число завершённых задач, время от начала до принятия и причины блокировок. Отдельно отмечается расход общего буфера. ## Упражнения с AI-инструментами для ЛР 2

Дата разбора: 07.11.2026. Ответы ниже получены при сценарном анализе проектной спецификации. Исходное решение для сравнения — документы в предыдущей редакции проекта. Разбор дополняет [симуляционную встречу по событиям](domain/session-simulation.md) и [сценарное ревью](reviews/lab2-simulation.md).

### 2Б. Контексты, агрегаты и инварианты

Запрос: «По 18 событиям из event-storming.md предложи ограниченные контексты и агрегаты. Отдельно назови инварианты, которые зависят от других агрегатов».

Предложение AI: Доступ, Начисления, Платежи и Прозрачность; Charge объединяет строки начисления, PaymentAttempt — попытку и полученные события, ExpenseReport — категории расходов. Ограничение одной активной попытки требует координации с Charge.

| Вопрос методички | Сравнение с проектом | Вывод |
|---|---|---|
| Разделение по сущностям или смыслу? | Доступ и Прозрачность совпадают; отдельные Начисления/Платежи различают состояния, но используют общий протокол погашения | Сохранены три контекста: Доступ, Расчёты, Прозрачность. Дополнительное разделение внутри Расчётов не даёт независимой поставки |
| Какие события объединены иначе? | AI оставил ChargePublished и PaymentConfirmed в разных агрегатах, как и исходная модель; quote выделен отдельно из-за срока согласия | Границы Charge, PaymentQuote, PaymentAttempt сохранены; их координирует application |
| Что требует других агрегатов? | «Начисление погашено только один раз» относится к Charge и PaymentAttempt, а не к одному объекту попытки | Нужны блокировка Charge, уникальный индекс и общая транзакция. Проверка роли также относится к сценарию доступа |

Преимущество предложенного разбора — явное отделение состояния попытки от согласованности погашения. Возможное разделение Начислений и Платежей оставлено условием дальнейшего пересмотра при независимых командах и изменении транзакционного протокола.

### 2В. Архитектурный стиль и цена выбора

Запрос с контекстом: «Выбери стиль для трёх человек на семестр: один учебный дом, FastAPI, три контекста, PostgreSQL, проверяемая оплата без повторного эффекта и один общий релиз».

Ответ AI: модульный монолит с отдельным worker. Общая БД позволяет атомарно изменить попытку и погашение; контексты остаются модулями с явными зависимостями.

1. «Назови цену выбора». Общая поставка, совместное масштабирование модулей, общая область отказа API, необходимость контролировать импорты. Worker масштабируется отдельно как процесс, но использует тот же доменный код и схему данных.
2. «Когда пересмотреть?» При появлении независимых команд, отдельных циклов поставки или измеренной нагрузки одного модуля; перед разделением нужен новый протокол согласованности платежа.
3. «Какой довод определяющий?» C-01 и NFR-02: небольшая команда и один атомарный финансовый результат. Скорость HTTP сама по себе не отличает монолит от микросервисов без измерений.

Сравнение с ADR-0003: стиль совпал. Исходная запись уже учитывала общую поставку; дополнительный разбор уточнил различие между независимым процессом worker и отдельным микросервисом. Слабое место обоих первоначальных описаний — промежуток между commit и сетью. После ревью добавлен сохраняемый протокол восстановления, ADR-0005 и AC-05.7/8.

Нейтральный запрос: «Стоит ли нам делать микросервисы?» Ответ без ограничений условный: они полезны при независимых командах и поставках, но добавляют сетевые отказы и распределённую согласованность. Полный контекст позволяет выбрать монолит; по одному слову «масштабирование» выбор не делается.

### 2Г. Контейнерная диаграмма

Описание для запроса (шесть предложений): «ДомПрозрачно обслуживает жильца, представителя УК и бухгалтера одного дома. Статический клиент поставляется nginx, а API на FastAPI содержит модули доступа, расчётов и прозрачности. PostgreSQL хранит данные, сессии и поручения на оплату. Отдельный worker восстанавливает created и сверяет pending через внешний тестовый провайдер. Провайдер присылает webhook, а планировщик стенда может запросить сверку. API и worker передают обезличенные журналы внешнему сборщику; отдельные кеш и брокер не предусмотрены».

Запрос: «Построй Mermaid-диаграмму контейнеров по описанию, не смешивая пользователей, доменные модули и процессы».

Полученный черновик: [container-candidate.mmd](exercises/container-candidate.mmd).

| Вопрос методички | Результат сравнения |
|---|---|
| Какие элементы попали на неверный уровень? | В этом черновике таких элементов не найдено: модули остаются внутри API, пользователи не изображены контейнерами, системы стенда снаружи |
| Какие связи без подписей или направления? | Таких связей нет. Для рабочей версии уточнены виды данных, версия технологий и номера лабораторных |
| Что добавлено сверх системы? | Дополнительных сервисов нет: описание явно исключает Redis и брокер. Черновик короче рабочей схемы и не заменяет её подробные подписи |

Вывод: подробное исходное описание снижает число лишних элементов. Рабочий источник — docs/architecture/c4/container.mmd; черновик хранится отдельно как результат упражнения. Автоматический рендер проверяет оба исходника. Полнота предметных решений проверяется по требованиям и сценариям восстановления, а не по успешному рендеру.
