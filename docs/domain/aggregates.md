# Агрегаты и транзакционные границы

Все денежные значения — целые копейки RUB. Равенство значений определяется содержимым; сущность сохраняет id при изменении.

## House

Корень: House. Контекст: Доступ.

### Состав

House — корень; адрес — значение; organisation_id — ссылка.

### Инварианты

Дом принадлежит ровно одной организации. Это условия любого сохранённого состояния; проверяются доменом и ограничениями БД.

### Что инвариантом не является

Право текущего пользователя — правило сценария, проверяется application через Доступ до изменения агрегата. Доступность провайдера — внешнее условие, проверяется адаптером.

### События

HousePrepared: house_id, organisation_id. Событие публикуется после успешного commit; повторная доставка потребителю должна быть безопасна.

### Границы и ссылки

Подготовка дома. Ссылки на другие корни — только по id.

## Charge

Корень: Charge. Контекст: Расчёты.

### Состав

Charge — корень; ChargeLine — сущность с id; Money и BillingPeriod — значения.

### Инварианты

Итог равен сумме строк; сумма 1–100000000 коп.; опубликованный документ неизменяем; один опубликованный документ на счёт/месяц. Это условия любого сохранённого состояния; проверяются доменом и ограничениями БД.

### Что инвариантом не является

Право текущего пользователя — правило сценария, проверяется application через Доступ до изменения агрегата. Доступность провайдера — внешнее условие, проверяется адаптером.

### События

ChargePublished: charge_id, account_id, period, amount_minor. Событие публикуется после успешного commit; повторная доставка потребителю должна быть безопасна.

### Границы и ссылки

Строки не живут без начисления; отдельный корень для каждого периода. Ссылки на другие корни — только по id.

## PaymentQuote

### Инварианты

Итог = основная сумма + округлённая half-up комиссия; версия условий и получатель неизменны; срок 10 мин. Это условия любого сохранённого состояния; проверяются доменом и ограничениями БД.

### Что инвариантом не является

### События

PaymentQuoteCreated: quote_id, charge_id, total_minor, expires_at. Событие публикуется после успешного commit; повторная доставка потребителю должна быть безопасна.

### Границы и ссылки

Отдельное предложение сохраняет точные условия согласия. Ссылки на другие корни — только по id.

## PaymentAttempt

Корень: PaymentAttempt. Контекст: Расчёты.

### Состав

PaymentAttempt — корень; PaymentEvent — сущность с внешним id; снимок предложения и Money — значения.

### Инварианты

Суммы попытки неизменны; финальный статус не откатывается; внешний event_id применяется один раз; ключ идемпотентности уникален для пользователя. Это условия любого сохранённого состояния; проверяются доменом и ограничениями БД.

### Что инвариантом не является

Право текущего пользователя — правило сценария, проверяется application через Доступ до изменения агрегата. Доступность провайдера — внешнее условие, проверяется адаптером.

### События

PaymentConfirmed / PaymentRejected: attempt_id, charge_id, amount_minor, provider_id. Событие публикуется после успешного commit; повторная доставка потребителю должна быть безопасна.

### Границы и ссылки

Одна попытка — одна транзакционная граница; ссылки на Charge и PaymentQuote только по id. Ссылки на другие корни — только по id.

## Межагрегатная согласованность платежа

Ограничение «одна активная попытка на начисление» и «одно погашение» — межагрегатные правила, не инвариант одного PaymentAttempt. Application блокирует строку Charge через SELECT FOR UPDATE, проверяет остаток и существующие created/pending/succeeded попытки, затем создаёт попытку. Частичный уникальный индекс charge_id для этих состояний страхует гонку. При отказе старая попытка остаётся, индекс освобождает право новой.

Проверенный успех обновляет PaymentAttempt и Charge.settled_attempt_id в одной транзакции PostgreSQL с блокировкой Charge. Это осознанная координация двух агрегатов внутри модуля, а не распределённая транзакция. Уникальный внешний event_id предотвращает повтор эффекта. Запрос к провайдеру выполняется после commit, без удержания блокировки; повтор — с тем же merchant id. Worker восстанавливает created и сверяет pending через API провайдера; порядок аренды и безопасного повтора задан в [протоколе восстановления](../architecture/payment-recovery.md). Если провайдер не гарантирует идемпотентность, интеграция блокируется до пересмотра ADR-0005.


### Порядок внешних ответов

Сохранённый attempt_id используется как merchant id. Если webhook пришёл до ответа create, аутентичное событие сопоставляется по merchant id с проверкой суммы и RUB (AC-05.6). Если контракт sandbox не передаёт merchant id и связать событие с попыткой пока нельзя, endpoint отвечает 503 для повторной доставки после получения provider_id; worker дополнительно сверяет попытку по API. До сопоставления payment_event не создаётся, неизвестная попытка не погашается. Поздний ответ create не понижает итоговое состояние. Повтор provider_event_id с другим payload_hash не применяется: несовпадение регистрируется для сверки (AC-05.5). Обычный идентичный дубль принимается без повторного финансового эффекта.
